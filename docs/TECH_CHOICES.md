# 技術の選び方と、その理由

Flick で使っている技術を一つずつ、「なぜそれを選んだか」「ほかの候補をなぜ選ばなかったか」の順に書いています。

## 全体の形

```
スマホ / パソコンのブラウザ
   │  ①画面（HTML・CSS・JS）  ②API（/api/...）
   ▼
Cloudflare Workers（1つのプログラムで両方を返す）
   ├─ D1（データベース：利用者・ログイン・タスク）
   ├─ Workers AI（Gemma 4：メモをタスクに分ける）
   └─ Google（ログインの確認だけ。公開鍵で本物か確かめる）
```

画面と API を同じ場所（同じドメイン）から出しているので、ログインのクッキーがそのまま使え、別ドメイン同士のやり取り（CORS）の設定が要りません。

---

## 1. 開いた瞬間にメモできるようにする工夫

いちばんこだわった所です。

| 工夫 | 理由 |
| --- | --- |
| 入力欄だけは、React ではなく素の HTML に書いた | アプリ本体の JavaScript（約 127KB）が届く前から打てるようにするため。HTML と CSS が届いた時点で使える |
| 入力を受け取る小さなスクリプト `boot.js`（約 1KB）を先に動かす | 送ったメモは端末の「受け箱」（localStorage）に入れ、アプリが起動したら取り出してタスクにする。読み込み中に書いても消えない |
| `autofocus` と、読み込み直後の `focus()` | パソコンでは開いた瞬間にカーソルが入っている。Android でも多くの場合そのまま打てる |
| Service Worker（`public/sw.js`）で画面を端末に保存 | 2 回目からは通信を待たずに画面が出る。電波がなくても開いてメモできる（通信が戻ったら送る） |
| ホーム画面に追加できる（`manifest.webmanifest`） | アプリのようにアイコンから一発で開ける |
| 日本語の変換を確定する Enter では送らない | `isComposing` と `keyCode 229` を見て判定。日本語入力で一番起きやすい誤送信を防ぐ |
| 文字の大きさは 17px | 16px 未満だと iPhone が入力時に勝手に画面を拡大して、メモの邪魔になる |

正直な制限：iPhone の Safari は、利用者が触る前にキーボードを出すことを許していません。そのため iPhone では「開く → 入力欄を 1 回タップ」が最短です（入力欄は画面のいちばん上・いちばん大きく置いています）。

## 2. 画面（フロントエンド）

### React 19 + TypeScript
- **選んだ理由**：画面を部品（カード、切り替え、通知…）に分けて作れる。TypeScript で型を付けると、データの形の間違いをビルドの時点で見つけられる。アニメーションの道具（Motion）が React 向けに一番充実している。
- **選ばなかった候補**：素の JavaScript（フリック・並び替えのアニメーションを全部自分で書くと数百行になる）、Svelte（軽いが、ドラッグとレイアウトのアニメーションを Motion ほど簡単に書けない）。

### Motion（旧 Framer Motion）
- **選んだ理由**：このアプリのアニメーションはほぼ全部これで書いている。
  - フリック：カードが指についてきて、離した速さと距離で「払ったか」を判断（`drag`）
  - 状態を変えたカードが、別の段へすっと滑って移る（`layout`）
  - 切り替えのガラスのレンズが伸び縮みしながら移る（`layoutId`）
  - 出てくる・消える動き、ばねの動き、数字がくるっと替わる動き
  - 「視差効果を減らす」設定の人には自動で動きを控える（`reducedMotion="user"`）
- **選ばなかった候補**：CSS だけ（指についてくる動きや、並び替えの動きは CSS だけでは作れない）。

### スタイルは素の CSS（Tailwind などは使わない）
- **選んだ理由**：Liquid Glass は「背景のぼかし（`backdrop-filter`）＋上から差す光＋ふちの屈折」を、疑似要素（`::before` `::after`）と `mask` で重ねて作る。こうした重ね合わせは、短いクラス名を並べるより、CSS の 1 か所にまとめた方が読みやすく直しやすい。
- 色や角の丸さは CSS 変数（`--doing` など）にまとめ、全体で揃えている。
- 文字は OS に入っている書体を使う。Web フォントを読み込むと、表示までの時間が延びるため。

### Liquid Glass の作り方
| 見た目 | やり方 |
| --- | --- |
| 透けて、後ろがぼける | `backdrop-filter: blur(24px) saturate(1.9)` |
| 上から光が差す | `::before` に白い放射グラデーション。カードを払うと光の位置が指の動きについてくる |
| ふちで光が曲がる | `::after` に、明るい縁から少し青みがかった縁へのグラデーションの細い枠 |
| ガラスが透かす色 | 背景に淡い青・桃・緑の大きな光をゆっくり漂わせる（白が基調のまま） |
| 重くならないように | 止まっているカードはぼかしを切る（背景はもともとぼけているので見た目は同じ）。ぼかすのは上の帯・切り替え・通知など、後ろを文字が流れる所だけ |

### 全画面のスケルトン
- HTML の中に、画面全体と同じ形の灰色の枠（スケルトン）を最初から書いてある。JavaScript が届く前の、いちばん最初の表示からスケルトンが出る。
- React が起動したら同じ形のスケルトンに引き継ぎ、データがそろったら、ぼけながら消えて一覧が順番に現れる。
- 一瞬だけ見えてチカチカしないよう、最低 0.45 秒は見せる。入力欄はスケルトンの間も使える。

## 3. 状態の操作（フリック）

| 操作 | 結果 |
| --- | --- |
| 右へ払う | 進める：未着手 → 進行中 → 完了 → 削除 |
| 左へ払う | 戻す：完了 → 進行中 → 未着手 |
| 左の丸を押す | 次の状態へ（未着手 → 進行中 → 完了 → 未着手） |
| カードを押す | 書き換え・状態の選択・削除 |
| 通知の「元に戻す」 | 直前の操作を取り消す（4.5 秒） |

- 「右＝前へ進める」「左＝戻す」に揃え、方向の意味を一つにした。
- 払っている間、カードの下から次の状態の色と名前が現れる。決まる所まで動かすと、アイコンが弾んで（対応する端末は小さく震えて）知らせる。
- 指でも、マウスでも、キーボード（丸のボタン）でも同じことができる。

## 4. サーバー（バックエンド）

### Cloudflare Workers
- **選んだ理由**：指定どおり Cloudflare を中心にした。画面のファイルと API を 1 つの Worker から出せる。世界中の近い場所で動くので速い。無料枠（1 日 10 万リクエスト）で個人利用には十分。
- **選ばなかった候補**：Cloudflare Pages（現在 Cloudflare は新しく作るなら Workers を勧めている）。

### Hono（API の道具）
- **選んだ理由**：Workers のために作られた小さな道具。「この URL に来たらこの処理」を短く書け、クッキーの読み書きも付いている。

### D1（データベース）
- **選んだ理由**：Cloudflare の中で使える SQL のデータベース（中身は SQLite）。「この人のタスクだけ」「新しい方が勝つときだけ上書き」を SQL 1 文で書ける。無料枠で足りる。
- **選ばなかった候補**：KV（書いた内容が世界中に行き渡るまで最大 60 秒ほどかかり、条件付きの上書きも書きにくい）、Durable Objects（このアプリの規模では仕組みが大きすぎる）。

### 同期の仕組み
- タスクの ID は端末で作る（`crypto.randomUUID()`）。電波がなくても先に追加でき、あとでまとめて送れる。
- 変更はいったん端末にためて、0.35 秒後にまとめて `/api/sync` へ送る。サーバーは「新しく更新された方（`updatedAt` が大きい方）」だけを採用し、最新の一覧を返す。
- 別の端末で開いたときや、画面に戻ってきたときにも同期する。

## 5. AI（Workers AI）

### モデルは Gemma 4（`@cf/google/gemma-4-26b-a4b-it`）
同じ 2 つのメモ（音声入力風・句読点なし）で、使える候補を実際に比べて決めた。

| モデル | 結果 | 1 回の消費（neurons） |
| --- | --- | --- |
| **Gemma 4 26B** | 誤変換を直し（「したがき」→「下書き」、「githubレポジトリ」→「GitHubリポジトリ」）、自然な「〜する」の形で分けた | 約 2.5〜3.5 |
| Llama 3.3 70B | 分け方は良いが、「下書き」が落ちる・英字の表記を直さない | 約 16〜20 |
| gpt-oss 20B | 考える過程に出力を使い切り、答えが空になった | 約 22 |
| Qwen3 30B | 答えが空だった | 約 2〜3 |
| GLM 5.3 Flash | 無料プランでは使えない | ― |

- **AI の仕事**：音声入力で一続きになったメモを、実行できるタスクに分け、誤変換を文脈から直す。メモにない作業は足さない。
- **出力の形を固定**：`response_format` に JSON の形（`{"tasks": [...]}`）を渡し、必ずその形で返させる。
- **速さと消費**：考える過程（thinking）を切り、すぐ答えさせる。
- **使いすぎ防止**：1 人 1 日 40 回まで。無料枠（1 日 10,000 neurons）なら 3,000 回ほど使える計算なので、余裕がある。
- **画面**：結果は一覧で見せ、外したいものを押して外してから追加する（AI の答えをそのまま入れない）。

## 6. ログイン（Google のみ）

### Google Identity Services（ID トークン方式・リダイレクト）
- **流れ**：Google のボタンを押す → Google の画面で選ぶ → Google が「この人は誰か」を書いて署名した ID トークンを、Flick の `/api/auth/google` に送ってくる → Worker が Google の公開鍵で署名を確かめる（`jose` という道具を使う）→ Flick のログインのクッキーを渡す。
- **選んだ理由**：
  - **秘密の鍵（クライアントシークレット）が要らない**。必要なのは公開してよい「クライアント ID」だけなので、秘密が漏れる心配がない。
  - **リダイレクト方式**にしたので、ホーム画面から開いたとき（ポップアップが使いにくい）でも動く。
  - ボタンは Google が用意したものを使う（Google の決まりどおりの見た目で、利用者が本物の Google だと分かる）。ガラスの台の上に載せている。
- **横取り対策**：ボタンを出すたびに使い捨ての値（nonce）を作ってクッキーに入れ、戻ってきた ID トークンに同じ値が入っているかを確かめる。
- **ログインの状態**：ランダムな 32 バイトの値をクッキー（JavaScript から読めない `HttpOnly`）に入れ、データベースにはそのハッシュだけを置く。ログアウトすればその場で無効になる。180 日使わなければ切れる（使っている間は延びる）。
- **アカウントの削除**：右上のメニューから、タスク・ログインの記録・AI の回数・利用者の記録をすべて消せる。押し間違えないよう、2 回押して確定する。
- **Google 側の設定**：Google Cloud にプロジェクト「Flick」を作り、ログインの画面（アプリ名・プライバシーポリシーの URL）を設定して「本番環境」に公開した。名前・メール・写真という基本の情報しか求めないので、Google の審査は要らない。
- **選ばなかった候補**：JWT をそのままクッキーに入れる方法（ログアウトしても有効期限まで使えてしまう）、Cloudflare Access（利用者を一人ずつ登録する、社内向けの仕組み）。

## 7. 安全のために

| 対策 | 内容 |
| --- | --- |
| 別サイトからの書き込みを断る | 書き込みの API は、`Origin` ヘッダーが Flick 自身のときだけ受け付ける（CSRF 対策） |
| ほかの人のデータに触れない | データベースの主キーを「利用者 ID ＋ タスク ID」にした。同じ ID を送っても、自分の分として別に入るだけ |
| 入力を確かめる | ID の形・文字数（500 字まで）・状態の値・時刻を Worker で確かめ、おかしなものは捨てる。SQL は必ず「?」で値を渡す |
| 読み込んでよい場所を限る | Content-Security-Policy で、スクリプトは自分と Google のログインだけ、ほかのサイトの中に表示させない、など |
| テスト用の入口 | `/api/auth/dev` は、手元（localhost）で `.dev.vars` に `DEV_LOGIN=1` があるときだけ開く。本番では 404 |

## 8. テスト（Playwright）

- **選んだ理由**：本物のブラウザを自動で操作して確かめられる。iPhone の Safari と同じ仕組み（WebKit）、Android の Chrome と同じ仕組み（Chromium）、パソコンの Chrome の 3 種類で同じテストを流す。
- テストは、本番と同じ形にビルドしたものを、本番と同じ仕組み（workerd）で手元で動かして行う。
- 公開中のサイトも、ログインなしで確かめられる項目を同じ 3 種類で確かめる（`npm run test:prod`）。
- Google での本物のログイン（ログイン → AI で分ける → 払う → データベースに保存 → 削除 → ログアウト）は、実際の Chrome で手で操作して確かめた。
- 確かめていること（33 項目 × 3 端末）：スケルトン、開いた瞬間のフォーカス、読み込み前のメモ、日本語変換中の Enter、フリック（マウスと指）、取り消し、編集、絞り込み、AI、ログイン前後の同期、別の端末での表示、ログアウト、アカウントの削除、プライバシーポリシー、未ログインの API、別サイトからの書き込み、ほかの人のデータ、おかしな入力、セキュリティのヘッダー、横のはみ出し、ガラスの効果、動きを減らす設定、オフライン、コンソールのエラーが 0 件。
